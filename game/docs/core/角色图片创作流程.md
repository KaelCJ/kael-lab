# DotaRogue · 角色图片创作流程

## 当前角色视觉政策

角色视觉不设必须原创的通用约束。用户指定 Warcraft III／DotA1 原型时，可以精确参考角色轮廓、武器、动作、施法姿势和特效；也可以接入已核对来源与许可证的外部资源。引入外部文件时，在角色 `manifest.json`、README 或制作记录中写明来源、许可证和改动范围。玩法数值、剧情、台词、音效和实际运行状态仍以本作代码与公开记录为准。

本文件下面的 Lanox 提示词和“从头重绘”文字是已有 Concept 产物的历史生成记录，不是当前角色视觉政策。新提示词应单独使用新版本，明确允许的 War3／DotA1 参考范围；不要回写旧任务的实际提交内容。

## 后续角色默认流程（2026-10-29）

这套流程适用于新角色、角色重做和 DotA1 皮肤；影魔已完成本地模型研究闭环，2026-10-29 又逐一用于其他八名英雄及 TB 恶魔形态，具体事实见[本轮制作记录](../sources/characters/dota1/model-study-20261029.md)。用户在认可角色与独立攻击反馈后，确认将这套做法沉淀为后续默认流程。2026-10-30 已将用户认可并确认可公开使用的模型派生帧接入正式静态目录，现行资源契约见[DotA1 来源与消费者](../sources/characters/dota1/README.md)；具体许可出处待用户补充。本地研究、正式静态接入、公开发布与完整实战验收分别记录。用户明确指定工具、来源或风格时，按用户指令调整，但仍保留下列记录和验收边界。

先以一个角色走通“来源→形体→动作→战斗反馈→真实入口验证”，确认方向后再逐个扩展。记录已获认可的资源和绘制版本，把它们列入回归对象；后续批量优化不能覆盖已认可的影魔动作或其他角色表现。遇到“不像”“丑”“动作奇怪”等反馈，先定位比例、身份特征、材质、动作还是特效脱节，再修改对应层。

1. **先写身份简报**：记录轮廓、头身比、身高、服装、武器／爪子、坐骑、搭档、双形态和关键动作。矮人火枪手与宙斯要先确认矮壮比例；宙斯的锤与斧不能因缩短身体一起缩小；卡尔的白衣和头顶三元素、影魔的黑色身体与长弯爪、露娜的骑手与坐骑接触关系、炼金的地精与食人魔组合、灵魂守卫的普通／恶魔两形态都要写进目标。
2. **先核对源和完整加载**：确认模型作者、来源、版本、文件哈希、使用条款和查看器版本；完整加载几何、骨骼动作、所有纹理、替换纹理和队伍纹理。按文件实际载荷识别纹理，不能只信扩展名；离线工具必须能在本地解析，不把正式 GitHub Pages 运行页绑到外部模型服务。
3. **先做单角色样片**：固定场景和相机，先导出一个角色的正面与侧面样片，在浅色、深色和游戏实际显示尺寸下检查身体、武器／爪子、火焰、留白、朝向、脚点和画布边缘。大图好看不能替代小尺寸可读性。
4. **再做可复现动作采样**：固定模拟步长、粒子预热、采样相位和本地随机种子，记录实际模型动作名称、时间区间和适配关系。采样随机数与游戏战斗随机数隔离；缺少 Dash 时可以适配 Walk，但必须在制作记录中说明。
5. **统一画幅、尺度和锚点**：一个形态的所有动作和方向共享像素尺度、相机约定、联合裁切、水平位置和脚点；禁止逐帧自动适配。联合边界必须给武器、爪子、火焰和其他粒子留空间，并分别检查身体可见高度与整张特效画布高度。双形态或骑乘结构允许有不同目标尺度，但过渡和锚点要单独记录。
6. **正确处理透明**：黑色身体和黑色爪子不能用纯黑色键抠图。加色粒子若导出黑色矩形，应保留原透明 pass，在完全相同的冻结状态下做黑底／白底双底重建；多背景检查单 PNG 对实时加色辉光的近似限制。
7. **接入可切换皮肤**：已认可并决定采用的成品帧必须进入所属游戏的正式 `assets/`，登记来源、哈希、姿态映射和真实消费者；原模型、候选帧及中间产物才留在 `.tmp/`。图片、显示尺度、脚点、武器锚点和攻击绘制适配成套接入，不把响应重写或临时研究服务当成正式运行依赖。普通皮肤保留为默认；DotA1 或其他新皮肤可改图片、显示尺度、视觉锚点和攻击表现，不改碰撞、生命、法力、冷却、属性、装备和技能规则。攻击衔接继续按下文[攻击动作与反馈](#攻击动作与反馈的逐角色流程)逐角色适配。保留旧存档与缺图回退，明确资源路径、姿态键和侧身命名。当前普通形态使用 `idle-a`、`idle-alt`、`walk-a`、`walk-b`、`dash`、`attack-windup`、`attack`、`attack-release`、`skill`；右向姿态在键名前加 `side-`。这 9×2=18 张是普通形态的当前资源契约，不是所有英雄的通用总量。
8. **从真实入口验收**：使用不改写响应的普通静态服务，从用户实际采用的游戏选择页和物理入口选择角色及皮肤，进入战斗；核对实际加载的脚本、PNG 路径和构建版本，不能用重新打开研究链接替代恢复。运行 `scripts/check_dota1_skin_delivery.py` 核对正式清单、完整映射、字节与显示参数；数旧 SVG 或确认 `.tmp` 文件仍在都不能证明交付。随后实际检查移动、朝向、自动攻击、主动技能、冲刺、暂停／恢复和换肤前后状态守恒；再分别记录静态资源、透明与尺寸、控制台／路径、可控预览和真实对局结果。浏览器尺寸模拟不等于真实触控，受控无脚本检查不等于原生关闭 JavaScript；自然触发、手动预览和未覆盖动作要分开写。

每个角色至少保留一份制作记录：身份目标；来源、作者、版本、哈希、纹理依赖与条款；查看器／导出工具版本；动作映射、采样步长、预热、种子和相机；共同画幅、裁切、尺度、锚点；透明方法及近似；普通／新皮肤的消费者路径和变更范围；证据、未覆盖项与保留／待清理产物。制作状态按“找到→下载→纹理完整→样片审阅”记录；接入范围（本地研究／正式静态站）、来源条件与验证结果另列，本地研究接入后也要走真实入口验证。正式接入须满足来源和再分发条件，并在正式构建重新验收，不继承本地研究的通过结论。社区重制模型只能称为社区资源，不能写成官方 DotA1 原模型。

影魔本地研究是本流程的示例：Snake Akuma 在 [Hive Workshop 的 Nevermore 社区模型页面](https://www.hiveworkshop.com/threads/nevermore-shadow-fiend-from-dota.372219/) 发布的社区重制 `HeroFlameLordV2_opt3.mdx`，使用官方 npm `mdx-m3-viewer@5.12.0` 离线导出正／侧各 9 张透明 PNG，经过统一画幅和黑白双底透明重建后，在本地游戏中验证了选择、攻击、Q、冲刺、右键移动、暂停与换肤状态守恒。`477×432`、约 `88%` 联合可见高度、`120/26` 显示参数、相机、种子、动作相位和预热时间都只是影魔案例参数，后续角色必须重新测量。该历史案例只覆盖离散样片和两种方向，没有证明连续 3D 动画、真实手机或其他英雄已完成；当时未核实模型与纹理的公开再分发条件。2026-10-30 的用户确认与具体许可出处待补状态，统一回源现行[来源记录](../sources/characters/dota1/README.md)。

本轮八英雄研究补充了三个可复用检查点：资源请求标为 SD 不保证 MDX 版本或历史原始字节，纹理后缀也不保证实际格式；兼容转换必须按真实字段处理并保留原文件，不能只改版本号。共同画幅要容纳整套动作的粒子，但游戏显示尺度应按身体和武器校准，避免剑圣旋风等大特效把人物缩成小点。黑色材质不等于缺图，模型空附件也不等于已有可见几何；分别核对纹理与节点后，再决定保留 TB 黑色恶魔、由 Canvas 绘制卡尔三元素等适配。

## 攻击动作与反馈的逐角色流程

模型的蓄势、出手和收势构成动作主体；额外轨迹帮助看清武器从哪里、在什么时候出手。先让身体和武器动作成立，再补短促、贴近武器的反馈。以下是后续制作要求；本轮实际完成和未测范围仍以[制作记录](../sources/characters/dota1/model-study-20261029.md)为准。

1. **清点现有绘制**：逐项列出源模型的武器／爪子、枪焰、烟雾、施法粒子，以及旧 Canvas 的实体武器、枪口、挥击、飞弹和命中反馈。对每一层注明保留、替换或仅在新皮肤抑制，并写清消费者。模型已有枪和烟时只补必要枪口短闪；卡尔模型没有可见三球时保留对应 Canvas。不能靠关闭整套特效解决局部重复。
2. **对齐真实出手事件**：从当前战斗实现读取攻击持续时间、实际出手事件及游戏时间，映射 `attack-windup`→`attack`→`attack-release` 的相位。蓄势不提前出现出手轨迹，出手后迅速消退，收势能回到待机或移动。远程的出手、飞行和命中分开核对，不能把枪口闪光当成已命中。视觉跟随实际攻速，暂停冻结、恢复不跳相位；不另建伤害计时器，不改变冷却、弹道或碰撞。制作记录中的出手比例只是当次实现的读数，不能写死为全角色常量。
3. **逐姿态测武器位置**：在对应形态、方向及攻击／收势 PNG 上量取枪口、手部、刀尖或爪尖，记录所用图像版本和像素坐标。若在最终裁切 PNG 上量点，直接共用图片的显示尺度、脚点、镜像、倾斜和抬升变换；若在未裁切原图上量点，先减共同裁切偏移且仅处理一次，再进入相同绘制变换。当前仅有前／侧投影时，不能直接把连续目标角度当成模型武器朝向；贴手轨迹按可见姿态适配，实际弹道仍沿玩法目标方向运行。双武器、骑乘与变身分别测量。
4. **保持每名英雄的动作语言**：火枪突出枪口，宙斯突出锤斧，影魔突出长爪与魂火，卡尔突出手部元素，月骑突出月刃，刚背突出短爪痕，炼金和剑圣突出各自刀锋，TB区分双刃与恶魔双爪。以本轮成功案例确定检查重点，颜色、长度、宽度、寿命和位置仍逐角色校准；不把所有英雄套成同一种大圆弧。反馈不能遮住身体、头部、武器和危险提示。
5. **保护皮肤与认可基线**：新增视觉分支限定到目标皮肤与形态；普通皮肤继续消费原有绘制。每完成一名英雄，回看该英雄普通／新皮肤，并回归影魔等已认可结果，再扩展下一名。换肤只替换视觉，核对属性、当前生命／法力、技能状态、装备与冷却；暂停换肤不能重建对局或触发攻击。
6. **用连续实战画面修正**：从选择页进入真实战斗，在游戏实际显示尺寸观察蓄势、出手、收势、移动中攻击与左右朝向，用连续截图或短录屏检查脱手、双发射点、悬空弧、遮挡和突跳。静态代表帧用于定位问题，不能代替自然连续动作。再覆盖相关攻速变化、暂停／恢复、变身恢复、减少动态效果与手机横竖屏；未实际操作的分支明确写为未测。每个角色写清本轮通过范围，保留失败版本证据。

### 可以复用的原则与必须重测的参数

| 对象 | 可以复用 | 每角色／形态必须重新确认 |
| --- | --- | --- |
| 身份与形体 | 先轮廓、比例和关键特征，再补细节 | 衣服、头身比、武器大小、爪形、搭档／坐骑与双形态 |
| 源模型与导出 | 完整加载、固定采样、共同画幅和真实透明 | 文件载荷、版本字段、纹理、动作序列、相机、预热和种子 |
| 显示与投影 | 同一形态共享尺度与脚点 | 身体目标高度、整帧边界、前／侧武器锚点及镜像变换 |
| 攻击反馈 | 模型动作优先、对应真实事件、短轨迹贴武器 | 源动作相位、当前出手时刻、原有粒子、旧绘制消费者、颜色与强度 |
| 验收与交付 | 真实入口、连续观察、皮肤守恒、认可版本回归 | 各英雄实测方向、动作、设备、装备及未覆盖项 |

### 本轮失败案例与修正方法

| 可见问题 | 原因与修正 |
| --- | --- |
| 角色配色变了，仍不像原型 | 只换皮肤未解决结构。回到身份简报：矮人／山丘的矮壮比例、卡尔白衣三球、影魔长弯爪等先成立，再处理材质。 |
| 黑色身体被抠掉，或特效带黑矩形 | 混淆黑材质与透明、忽略加色粒子。保留材质，冻结同一状态做透明重建，并检查浅／深背景。 |
| 大特效完整了，人物却缩成小点 | 把整帧特效边界当作身体显示高度。画幅容纳全部动作，人物尺度另按身体和武器测量。 |
| 火枪同时从枪口与腰部开火 | 模型枪焰与旧 `muzzle` 等消费者叠加。仅在目标皮肤替换重复层，按前／侧模型枪口补短闪并保留源烟。 |
| 炼金／剑圣出现悬空括号或大弧 | 连续目标角度与离散模型投影不一致。按对应攻击／收势帧的刀尖测点，共用图片变换，改成局部短残迹。 |
| 批量优化后已认可动作消失 | 扩展时覆盖了已有绘制或共用分支。保留已认可版本和消费者记录，限定新增范围，逐角色回归。 |
| 研究入口正常，普通入口却换回旧皮肤 | 被采用的 PNG、尺度和攻击反馈长期只由临时服务改写响应。成品及配套接线进入正式资源，以普通静态服务和用户原入口重新验证，检查脚本不得依赖 `.tmp`。 |

### 每角色交付记录的补充项

沿用上文的一份制作记录，补齐以下内容，不再建立第二套平行记录：

- 已认可基线、此次修改的角色／形态／皮肤，以及源模型与 Canvas 各层的取舍。
- 动作相位与真实出手事件的对应关系、每姿态武器锚点和显示变换；案例参数标明适用范围。
- 同一构建下的实际尺寸连续画面、普通／新皮肤与已认可角色回归、暂停及状态守恒结果。
- 自动检查、静态审图、受控预览、自然实战分别列结果；减少动态效果有代码分支不等于偏好实测通过，模拟视口不等于真实触控。
- 来源／再分发条件、接入范围、证据与未覆盖项、产物保留／待清理清单；不把短局通过写成全方向、全装备或长局通过。

## 历史／可选的 Concept 路线（2026-10-11～2026-10-28）

以下记录保留早期 Lanox Image2 首图、AI／SVG 对照和任务协议，供回溯来源使用；它们不是后续角色的默认制作路线。历史任务的凭据状态只代表当时的本机检查，不能推断当前凭据仍可用。

## 历史旧图的实际来源

历史上 `game/static/dotarogue/assets/art/` 的初版与像素图属于另一条旧制作路线（迁移前位于 `game/art/`）。已从归档制作记录核对：初版直接编写 SVG；角色、武器、敌人、技能与地图像素资源由 Python 的色板、矩形或多边形绘制后导出 SVG。浏览器截图与拼版只是预览，不能当作模型出图证据。这些旧图未被证明通过 Lanox Image2 生成，当时六名英雄改用真实 Image2 位图创作。

## 历史 Lanox 图片任务与产物

1. 读取本角色的 `art/concept/<id>-idle-v1.prompt.md`，保留 DotA1／War3 原型和 Kingdom Rush 的精致手绘小角色方向。每名英雄独立生成一张全身待机图；炼金术士完整包含地精与食人魔搭档。
2. 创建真实 Lanox Image2 异步任务：`POST https://api.lanox.ai/api/v2/lanox-images/generations`；使用模型 `lanox-image-2`、`aspect_ratio=3:4`、`resolution=2k`、`n=1`。使用稳定的幂等键；已有任务只继续查询，不因等待而重复创建。
3. 按返回的任务 ID 查询 `GET https://api.lanox.ai/api/v2/lanox-images/tasks/<id>`。`queued`／`processing` 表示等待；`succeeded` 后才下载 `data[0].url`，下载图片时不附带接口鉴权头。失败如实记录。
4. 此协议没有原生透明背景参数，先以无阴影、无渐变的纯色键背景出图，再用本机图像工具去除背景并保存真实 alpha。若原图已含有效 alpha，直接保留。原始图片保存为 `<id>-idle-v1-source.png`，所选透明图为 `<id>-idle-v1.png`；原始图与透明图都必须来自真实生成结果，已有版本不覆盖。
5. 以长边为准生成等比例的 128px／64px PNG 预览，查看原图与缩小图，核对完整身体、武器或自然武器、角色身份、轮廓可读性和背景边缘。除色键残留外，还检查浅／深背景上的半透明灰点与画布外框；清理时另存版本并保留原图。发现问题时按具体缺陷调整，避免盲目重复计费。
