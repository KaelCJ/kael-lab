# 特效制作规范

适用于《DotaRogue》新增或修改元素、命中、弹道、持续场域与装备反馈。以下是后续制作应遵守的约束，不代表现有特效已全部达标，也不要求本次批量改造旧实现。具体制作步骤和记录模板见[特效制作方法论](特效制作方法论.md)。

本规范拥有通用约束；[通用战斗特效](通用战斗特效.md)拥有当前模块、素材、消费者、具体 API 与已知限制；[视觉规范](视觉规范.md)拥有游戏主题和素材风格。任务中的决定、过程与验证证据留在对应工作项，长期文档不复制执行日志。

## 表现必须服务真实事件

- 制作前明确要表达的事件、观看尺寸、锚点、方向、持续时间，以及起势、主体、命中或收尾的关系。持续场域和瞬时命中不必采用相同阶段，但必须说明何时开始、何时结束。
- 在实际显示尺寸下，仅凭轮廓和运动也应能分辨主要效果；火、冰、风、雷不能只靠换色区分。强度和装备等级可以改变局部细节，但不能只靠无限增加面积或亮度表达升级。
- 玩法系统负责目标、伤害、控制、暴击、范围及冷却。表现模块只消费已确定的事件与必要数据，不额外判定命中或调用伤害逻辑；降低特效细节不得改变玩法结果。仅替换表现时，视觉下落、蓄势或消散不得推迟伤害、暂停移动或延长技能寿命。
- 危险预警、有效范围、玩家位置和血条保持可辨。装饰光晕可以超出命中范围，但不能让玩家误判可躲避边界。暴击强调附着真实暴击事件，不使其他技能自动获得暴击能力。

## 代码与素材按所有权存放

下表使用仓库根目录相对路径；`<effect-id>` 是稳定的语义 ID，如 `wind`。只创建当前确实需要的文件和目录，不要求每种效果同时拥有 JS、SVG、PNG 三类素材。

| 位置 | 保存什么 |
| --- | --- |
| `game/static/dotarogue/js/effects/<effect-id>.js` | 该效果的加载、更新或绘制实现；模块按真实职责拆分。 |
| `game/static/dotarogue/assets/art/effects/<effect-id>/svg/` | 可编辑矢量形状，如流线、碎片、符号。 |
| `game/static/dotarogue/assets/art/effects/<effect-id>/png/` | 透明纹理或实际使用的帧图，如烟、尘、柔光。 |
| `game/docs/sources/art/effects/<effect-id>/` | 必需的可编辑源或离线生成脚本；来源及许可按实际需要随素材保存。 |
| `game/static/dotarogue/effects.html`、`game/static/dotarogue/css/effects.css`、`game/static/dotarogue/js/effects-preview.js` | 现有预览入口与控制器；按实际需要扩展，不为每个元素复制整套预览框架。 |

特效保持游戏私有。角色身份与姿态素材继续归角色目录；两个英雄使用同一风效果，也不构成上收到全站 `shared` 的理由。先列清真实消费者和不适用对象，再提取稳定机制，不预建所有元素目录、无消费者注册表或统一引擎。

素材路径相对于模块或所属页面解析，适应 GitHub Pages 项目子路径，不依赖本机绝对路径。源图、生成输出和运行消费位置必须可追溯；离线工具不成为浏览器的安装或运行时构建要求。

## 调用契约必须明确

每个效果只暴露消费者实际需要的参数，不强制复制风的工厂名、参数表或算法。其当前契约至少说明：

| 契约项 | 必须回答的问题 |
| --- | --- |
| 坐标与尺寸 | 世界、屏幕还是局部坐标；锚点在哪里；角度方向、单位、基准尺寸和可见外扩范围是什么；谁应用相机与 DPR。 |
| 时间与状态 | 输入是秒数、归一化进度还是增量；暂停、恢复、重播如何处理；谁拥有实例、生成、结束和清理。 |
| 参数语义 | 哪些参数可实时改变，范围与默认值是什么；颜色、强度、等级是否影响相位或缓存。 |
| 加载与失败 | 哪些素材需要预加载、何时可画、失败如何显示或回退、重复进入是否重复加载。 |
| 消费者 | 哪些预览、英雄、装备或敌人已实际调用；哪些仍为候选；破坏性变更需同步哪些入口。 |

共用预览按当前元素显示有效控件，不让没有旋向等能力的效果暴露无效操作。观察尺寸说明以主体还是包含烟雾、光晕的外扩范围为基准；小尺寸样张不能标作战斗接入证明。预览入场的透明度、缩放包络由消费者明确管理，不直接当作战斗事件的持续时间或收尾。

战斗时间由战斗循环提供；表现模块不启动私有 RAF 或用墙上时钟绕过暂停。可用确定性的时间函数，也可由调用方推进有限状态；装饰随机与战斗随机序列分离，重播核对时保留种子或确定性输入。调用方停止时间时，视觉状态也应停止。

需要随位移变化的表现以玩法实际完成的移动为依据，区分位置、方向与累计行程；不能用理论速度乘时间绕过阻挡、滑动或转向。预览可使用明确标注的虚拟行程，但不据此证明真实路径和碰撞行为。

纯绘制函数保存并恢复 Canvas 状态，包括透明度、变换、混合模式、裁剪和图像平滑；不得把局部设置泄漏到后续对象。除拥有整张画布的页面外，不清空调用方画布。事件订阅、定时器、实例列表和缓存均由明确的所有者管理，结束或离开时按生命周期释放或保留。

多效果异步加载须明确缓存由模块还是消费者持有，区分复用渲染实现与共享运行实例，不能把单次工厂初始化称为全局复用。过期请求不得覆盖当前选择、说明或播放状态；失败应允许重试，并与其他可用效果隔离。

## 优先研究开源技术，逐项记录采用方式

先检查现有实现及 GitHub 等公开项目，寻找形状、轨迹、时间、缓存或预算方面的适用机制；候选不适用时记录原因再自行实现，不为“用了开源”搬入整个游戏框架。

对实际采用或改编的候选，记录仓库、具体文件、核对日期、固定提交／版本；若无法取得固定版本，记录所读文件的摘要值及该限制。区分三种采用方式：

| 采用方式 | 来源与交付要求 |
| --- | --- |
| 技术思路参考 | 写清借鉴点、适配差异和没有采用的依赖；不声称上游提供了不存在的成品效果。 |
| 代码复制或改编 | 核对对应代码许可，保留所要求的版权和完整许可证文本，标明修改范围。 |
| 素材直接使用或修改 | 单独核对该图片、纹理、字体或音频的作者与许可，落实署名、再分发等条件。代码仓库的 MIT 不能自动证明全部素材可用。 |

公开可见不等于可以再分发；来源或许可未明确的文件不进入公开资源。当前已核对的参考及风、火的采用边界见[通用战斗特效](通用战斗特效.md)，后续引用仍核对所采用版本。

## 运行成本与降级要可测

- 素材解码、SVG 栅格化和可复用纹理生成放在加载或必要的参数变化阶段，避免逐帧重复；缓存按实际消费者复用，同时说明尺寸、数量与释放边界。
- 按当前消费者声明单实例工作量、同屏实例预算、触发频率和结束回收方式。预览阶段只记录预览负载，未来战斗预算标为目标或待测，不把模块参数写成全局性能保证。粒子数、路径采样、透明叠加面积、贴图尺寸和 DPR 都影响成本；风的具体数值不是其他效果的统一预算。
- 先测量再优化。只有真实分配或回收压力值得处理时才引入对象池；模糊、混合或逐帧路径等手段按实测取舍，不用“全部禁止”代替性能判断。
- 超预算优先减少非关键碎屑、尘雾和装饰层，保留命中位置、危险边界与主要形态。减少动态效果设置应降低闪烁和非必要运动，并保留玩法信息。
- 性能记录包含设备、浏览器、视口／DPR、实例数量、触发密度、运行时长和测量指标，如帧耗时分位数、慢帧比例与内存趋势。未测的数据写未测；GIF 流畅、用了缓存或限制了粒子数均不能证明目标设备达标。

## 交付状态与证据对应

| 可声明状态 | 所需证据 |
| --- | --- |
| 设计／Concept | 目标、事件、视觉拆解与来源已写；不代表有素材或实现。 |
| 预览已实现 | 当前模块有真实预览消费者与可达入口；未完成视觉或交互验收时明示。Current 必须限定为预览能力。 |
| 指定预览流程已验证 | 从真实预览入口核对画面与操作，明确实际验证的尺寸、背景、动态、输入和异常状态及未覆盖范围。 |
| 战斗已接入 | 当前源码有真实事件消费者；逐项列出接入位置及尚未完成的实战验收。 |
| 指定战斗流程已验证 | 从游戏选择入口走真实获取／施放／命中／结束链路，核对画面及业务结果，记录设备、主题、场景和未覆盖范围。 |

前端变更按项目现行规则验收直接页面和真实消费者，覆盖适用的桌面、手机横竖屏、主题、键盘与触控、暂停恢复、资源与控制台；截图逐张观察并核对关键控件计算样式。动态效果另看连续画面，不能只用一张截图。异常状态不可真实进入时明确记为未验收。

语法、资源解析、隔离测试、结构扫描、视觉观察与真实流程分别报告。多消费者复用须逐个登记并验证，独立预览不能证明战斗遮挡、手机硬件性能或长局表现。规范已写入只代表文档产出；后续任务实际采用后，才能记录方法的复用验证。
