# 认知拉齐

## 性能问题全景

### 五类主要问题（按影响排序）

1. **资源加载问题**（高影响）
   - 角色资源 32MB，占游戏总资源 38MB 的 84%
   - scavenger 单个英雄 17MB（PNG+SVG+WebP 三格式并存）
   - 预加载所有 9 个英雄，玩家只使用 1 个
   - 每次进入游戏重新加载，无跨对局缓存

2. **碰撞检测算法低效**（高影响）
   - O(n²) 朴素算法：每个子弹检测所有敌人
   - 后期密集场景：30 子弹 × 80 敌人 = 2400 次/帧
   - 60 FPS 下 = 144,000 次碰撞检测/秒
   - 缺乏空间分区优化

3. **重复距离计算**（高影响）
   - 每帧 16+ 处 `for (const e of run.enemies)` 循环
   - `distance()` 在碰撞、装备被动、技能范围中被重复调用
   - `updateBullets` 中每个子弹多次计算到同一敌人的距离

4. **数组操作低效**（中影响）
   - 154 处 `.map/.filter/.forEach` 操作
   - 反模式：`filter().sort()[0]`（排序全部只取最小）
   - 反模式：`run.enemies = run.enemies.filter(e => !e.dead)`（创建新数组）
   - 缺乏对象池，子弹/特效频繁创建销毁触发 GC

5. **Canvas 渲染开销**（中影响）
   - 543 处 Canvas 绘制调用
   - 静态地面每帧重绘（即使摄像机不动）
   - 火焰特效每帧 50+ 次复杂操作（三角函数、贝塞尔曲线）

### 性能目标（待用户确认）

- **桌面**：全程 60 FPS（16.67ms/帧）
- **移动**：前 15 波 60 FPS，后期 50+ FPS（20ms/帧）
- **加载时间**：桌面 < 3s，移动 4G < 5s（当前待测量）
- **内存占用**：降低 40%+

## 优化策略共识

### 三阶段路线图

**阶段 1：快速优化**（1-2 天，预期 FPS +20-30%）
- 距离计算缓存（每帧开始计算一次敌人到玩家距离）
- 数组操作优化（filter/sort 改线性查找）
- 地面层离屏缓存（静态内容不重绘）
- 移除冗余 PNG 资源（保留 WebP+SVG）

**阶段 2：结构优化**（3-5 天，预期 FPS +30-40%，加载 -60%）
- 空间分区系统（网格或四叉树）
- 按需加载角色资源
- 对象池（子弹、特效、粒子）
- HUD 差异化更新

**阶段 3：高级优化**（可选，1-2 周，支持 200+ 敌人）
- WebGL 渲染管线
- Web Worker 物理计算
- 导航网格优化
- 代码分割

### 优先级原则（待确认）

- P0 必做：空间分区、按需加载
- P1 高价值：距离缓存、离屏渲染
- P2 性价比：数组优化、对象池
- P3 锦上添花：HUD 优化、特效分级

## 关键约束与边界

### 必须遵守的边界

✅ **不改变游戏性**：玩法、数值平衡、视觉风格保持不变  
✅ **保持兼容性**：现有角色、装备、技能系统正常工作  
✅ **通过现有测试**：选择页进入、波次流程、暂停恢复、工作台演示  
✅ **移动端不损害桌面**：可分级实现（质量选项），但不能"只优化桌面"

### 实施原则

- **测量驱动**：每阶段完成后测量实际 FPS 提升，与预期不符时调整
- **算法优先**：不能依赖"用户设备性能好"的假设
- **可读性**：复杂优化必须注释说明原理
- **增量验证**：每项优化独立可验证，不等全部完成

## 容易误解的概念

### 误解 1：优化 = 重构

**澄清**：性能优化不是代码重构。重构改善结构但不改变行为；性能优化改变内部实现方式（算法、数据结构），但外部行为必须一致。

**判断原则**：优化后的代码如果通过相同的测试用例，就是正确的。

### 误解 2：空间分区很复杂

**澄清**：简单的网格分区（Grid-based Spatial Hashing）实现只需约 50 行代码，性能提升显著。不需要立即上四叉树或 R-tree。

**参考实现**：
```javascript
// 伪代码示意
const GRID_SIZE = 200;
const grid = new Map(); // key: "x,y", value: entity[]

function updateGrid() {
  grid.clear();
  for (const e of entities) {
    const key = `${Math.floor(e.x / GRID_SIZE)},${Math.floor(e.y / GRID_SIZE)}`;
    if (!grid.has(key)) grid.set(key, []);
    grid.get(key).push(e);
  }
}

function getNearby(x, y) {
  const key = `${Math.floor(x / GRID_SIZE)},${Math.floor(y / GRID_SIZE)}`;
  return grid.get(key) || [];
}
```

### 误解 3：按需加载会让代码复杂化

**澄清**：当前 `loadArt()` 已经是异步加载，改为按需加载只需：
1. 将 `HERO_ART` 和 `HERO_POSE_ART` 拆分为 9 个英雄的独立列表
2. 在选择英雄后只加载该英雄的资源
3. 保留当前的 Promise.all 机制

**关键点**：不需要改变图像使用方式，只需要改变"何时加载"。

### 误解 4：对象池会引入复杂的生命周期管理

**澄清**：对象池的核心是"重置状态"而非"复杂管理"。当前代码已经有明确的创建（`run.bullets.push`）和销毁（`splice`）逻辑，改为对象池只需：
1. 预分配对象数组
2. 销毁时重置状态并放回池中
3. 创建时从池中取出（或扩容）

**判断原则**：如果对象有明确的"死亡"标记（如 `e.dead`, `b.life <= 0`），就适合用对象池。
