# 新增武器工作流

本流程适用于《DotaRogue》所有 `kind: "finished"` 成品装备的新增、修改，以及为已有成品补齐成长；防御、鞋、吸血、物理或法术定位不改变适用性。先读 [游戏 README](../README.md)、[装备逐件设计](装备逐件设计.md)、[成品武器升阶设计](成品武器升阶设计.md)；涉及界面或绘图时，继续按 `game/AGENTS.md` 加载相应专题。源码与真实页面决定当前状态，设计方案不能代替已实现能力。

全部成品必须同时具有固定配方和 **Lv.1／Lv.2／Lv.3** 三档成长，保留三件同名同级合一、最高三级、属性和总卖价守恒的规则。只有组件和中间件不参与三合一；不能因“不是输出武器”而排除先锋盾、动力鞋、撒旦之邪力等成品。此规则已由用户明确确认，不由 Agent 自行缩小范围。只完成 Lv.1 时只能报告该阶段完成，不能称整件装备完整交付。

## 当前形态进化基线

当前狂战斧、红杖、分身斧接入真实攻击形态变化、角色身边的持续装备实体与共享三语言阶段说明；其余 17 件仍为既有属性／被动数值成长、短特效或通用升阶反馈，不能因为具有 Lv.1～Lv.3 就宣称全部完成形态进化。三条的当前完整契约见[成品武器升阶设计](成品武器升阶设计.md)。本轮已完成工作台、图鉴、移动尺寸页面及输入检查；自然局仅取得一级分身斧与狂战斧并带入战斗，未自然取得红杖或高阶，长期平衡仍未验证。具体范围见[游戏 README](../README.md)。

| 装备 | Lv.1 | Lv.2 | Lv.3 | 保留与分配边界 |
| --- | --- | --- | --- | --- |
| 狂战斧 | 首目标中心分裂，半径 88 | 玩家中心朝首个命中方向横扫 200°，半径 108 | 玩家中心环斩 360°，半径 132 | 原系数 35%／45%／60%；仅近战有效普攻，每次攻击一次，均排除首目标 |
| 红杖 | 最多 1 目标 | 最多 2 目标，副目标限 90° 扇面 | 最多 3 目标，副目标限 150° 扇面 | 保留每 6 秒、射程 500、总基础预算 38／76／114 + 法攻 × 0.7；单目标全额，多目标主副权重 2:1:1，按实际目标数重分配 |
| 分身斧 | 每 5 次有效普攻发射 2 道 | 同周期发射 4 道 | 同周期发射 6 道 | 总倍率 130%／170%／220% 在各弹间均分；半展开角 0.16／0.35／0.55 弧度，等级在发射时快照并保持全寿命 |

红杖主目标仍优先精英／首领；全部目标都必须满足射程与地形无遮挡，副目标还须满足以玩家至主目标方向为轴的对应扇面。缺少副目标不丢弃预算，没有合法主目标不消耗就绪状态。三条的派生伤害均不暴击、不吸血、不触发装备或英雄普攻命中被动及普攻计数；基础属性、配方、售值及一级原有数值保持兼容。

玩法思想参考 [Canvas Vampire Survivors 的固定版本武器实现](https://github.com/ricardo-foundry/canvas-vampire-survivors/blob/e616704889e57efc9c1f49098786a95c364008d3/src/weapons.js)，提交 `e616704889e57efc9c1f49098786a95c364008d3`，MIT。仅借鉴升阶改变攻击布局的思路，未复制上游源码、素材或依赖；不能把来源游戏的实现或能力写成本作已经实现的内容。

## 一个目标一个工作项

开始设计和修改前，使用本仓库的 [nest-work-item Skill](../../.agents/skills/nest-work-item/SKILL.md) 创建或定位一个可追踪目标。先按 Skill 的索引方法校验，在当前及归档项中按武器名称、成长目标查重，完整读取相似项 README 判断是否等价；命中等价项时沿用入口，不重复建项。创建路径按 Skill 返回已有入口后结束；任务还要求继续实施时，再进入继续工作项方法。无法唯一定位或索引校验失败时，按 Skill 保留现场并处理阻塞，不手编编号或覆盖索引。

新项的 ID、目录、根 README、原始需求、索引登记和写后校验均使用 Skill 当前方法与工具。独立新增一件武器对应一个目标，不为三个等级分别建项；同一授权任务批量补齐多件成品可共用一个工作项，但须逐件列出交付和验证范围。后续需求、方案、执行和测试事实使用 Skill 的更新路径回写。

## 执行顺序

1. **需求与边界。** 写明武器定位、近战／远程／技能适用性、成品分类、获取方式、配方及本次范围。确认名称与素材来源可公开；复用现有功能前核对当前源码，不引用旧武器槽草案推定行为。
2. **三档设计。** 一次列出 Lv.1／Lv.2／Lv.3 的可加属性、特色被动、触发资格与频率、目标数／范围／持续时间、同类取强规则、属性上限、成本／卖价和十二格制作路径。涉及形态进化时，另写清阶段名称、判定中心／方向／角度、每次攻击去重、主副目标筛选、单次总伤害与逐目标／逐弹分配、缺目标处理及弹丸等级快照。为每档写明对应特效、命中信息、两主题表现与动态效果预算；既有一级数值保持兼容，新增乘区要解释收益。没有新被动或分级战斗装饰时，明确保留现有行为并复用等级徽标与升阶反馈，不为凑等级虚构技能。方案未接线前标为目标。
3. **定义与战斗。** 在 `equipment.js` 的同一装备定义及 `EQUIPMENT_UPGRADES` 中接入三档，全部 `kind: "finished"` 的 ID 集合必须与 `EQUIPMENT_UPGRADES` 键集合完全一致，通过现有 `resolveEquipment`、出售和描述函数统一取值；在 `game.js` 接通战斗触发、配方和商店来源。形态字段与数值字段都由共享定义驱动，检查须按字段类型验证，不能把 `mode` 等合法枚举误作非有限数值。派生命中不回流普攻被动和计数；实际几何与目标列表传给绘制，弹丸发射时快照等级，不能让短装饰寿命决定弹丸外观。沿用现有图标，新增物品才补齐对应图标及来源记录。不要复制三个独立装备定义，也不要让装饰特效改变伤害、触发次数或战斗随机数。
4. **完整界面。** 同步商店商品、固定配方、库存升阶／预览／出售、HUD、暂停及图鉴。简体、繁体、English 都要呈现强化等级、实际属性／被动和上限；图鉴保留三级对照、三合一资格和无 JavaScript 文字版。已实现的形态进化还须在全／简说明中一致呈现阶段、真实覆盖区域、弹数／目标数及伤害分配，持续装备实体与真实弹丸要让玩家看出等级差异；徽标和 0.24 秒短装饰不代替持续形态。基础等级、合成阶段与强化 Lv. 分开，鼠标、键盘和手机都能完成操作。
5. **分层验证。** 先做语法、资源与有意义的数值逻辑检查：全量比较 finished 集合与升级表集合完全一致、逐件确认成品有有效且可从基础组件取得的固定配方，再检查三档成长、同级三合一、混级／不足／非适用／满级／重复点击／满格边界、属性／总卖价守恒、资源与冷却不刷新、同类被动取强及防递归。三条进化另按[专项验收](成品武器升阶设计.md#首批三条进化的专项验收)核对真实几何、红杖实际 1／2／3 目标预算、分身 2／4／6 弹总预算和超过短装饰寿命后的等级快照。工作台分别对比两主题、左右朝向、正常／减少动态效果、三件共持和手机尺寸，检查遮挡与实际命中节点。随后使用本次构建，从 `games.html` 真实进入，获得材料或成品、合成、升阶、带入战斗并核对最终效果；检查桌面键鼠、手机横竖屏触控、暂停／转屏／焦点、三语言、两主题、控制台、静态资源及无 JavaScript 可读性。界面改动按前端规则实际查看截图和计算样式。工作台、注入装备、固定随机数或直接调用函数只能记录为受控检查，不能替代真实获取流程；未执行浏览器检查时明确保留为未验证。
6. **记录交付。** 按工作项的需求／方案／执行／测试路径记录已发生事实，在 `game/README.md` 和对应装备、商店、界面、协作上下文专题更新当前能力与验证入口。列明实际武器、等级、波次、主题、语言、设备和证据；未取得的高阶、未到达的波次与平衡风险单列，不用其他武器或旧构建的验证代替。提交、推送和发布仍取决于当前任务授权。

## 完成检查表

- [ ] 已定位或创建唯一工作项，用户需求与本次范围可回源。
- [ ] 全部 finished ID 与 `EQUIPMENT_UPGRADES` 键完全一致，每件成品都有可达固定配方；组件和中间件均未获得三合一资格。
- [ ] 三档属性、被动、经济、特效已设计并同步接入；沿用现有行为和通用反馈的成品已如实说明，基础等级语义正确。
- [ ] 本次涉及的形态进化已逐档说明并核对几何、目标／弹数、总预算与分配、缺目标处理、触发去重及等级快照；没有将其余数值升阶泛称为形态进化。
- [ ] 共享定义、战斗、素材、商店、HUD、暂停、三语言图鉴与无 JavaScript 说明一致。
- [ ] 持续装备实体、完整弹丸寿命、减少动态效果、两主题、左右方向及三件共持的视觉证据已分别记录；未检查项未写成通过。
- [ ] 数值逻辑检查、真实获取／升阶／战斗、布局与视觉检查分别记录，未覆盖内容明确。
- [ ] 工作项与游戏专题已按事实更新；只实现或验证部分等级时明确报告剩余范围。
